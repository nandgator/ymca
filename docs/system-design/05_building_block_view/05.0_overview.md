# 05.0 — Building Block View: Overview

The static decomposition of the system. This section defines the bounded
contexts, what each owns, and how they are permitted to talk to each other.
Subsections 05.1–05.9 elaborate one context each.

The critical rule: **domain services never implement their own authorization
rules.** They ask.

```txt

```

## 5.0.4 Context relationships

```txt
                    ┌──────────────┐
                    │ Organization │  upstream of everything;
                    │              │  defines the tenant that
                    └──────┬───────┘  every other context requires
                           │
        ┌──────────┬───────┼────────┬──────────┐
        ▼          ▼       ▼        ▼          ▼
  ┌──────────┐ ┌────────┐ ┌──────┐ ┌────────┐ ┌──────────┐
  │ Identity │ │Governance│ │Policy│ │Finance │ │Safeguard │
  └────┬─────┘ └────┬───┘ └───┬──┘ └───▲────┘ └────┬─────┘
       │            │         │        │           │
       │      confers roles   │        │      gates roles
       ▼            ▼         ▼        │           │
  ┌──────────────────────────────┐     │           │
  │        Membership            │─────┘           │
  └──────────┬───────────────────┘                 │
             │ entitlement                          │
      ┌──────┴───────┐                              │
      ▼              ▼                              │
┌──────────┐   ┌──────────┐                         │
│Programme │   │ Resource │◀────────────────────────┘
└──────────┘   └──────────┘        clearance required
                                    for instructor roles
```

**Relationship patterns**, in DDD terms:

| Upstream → Downstream     | Pattern            | Note                                              |
| ------------------------- | ------------------ | ------------------------------------------------- |
| Organization → all        | Conformist         | every context accepts the tenant model as given   |
| Identity → Membership     | Customer/Supplier  | Membership depends on Person identity             |
| Membership → Programme    | Customer/Supplier  | enrollment checks membership entitlement          |
| Membership → Resource     | Customer/Supplier  | resource entitlement derives from subscriptions   |
| Policy → all              | Open Host Service  | published evaluation interface                    |
| Safeguarding → Governance | Conformist         | clearance gates role assignment                   |
| Finance ← all             | Published Language | charges raised via a shared charge vocabulary     |
| Membership → Consumption  | Customer/Supplier  | entitlement to consume derives from subscriptions |
| Resource → Consumption    | Conformist         | a record may realize an allocation (05.10.2)      |

## 5.0.5 What each store owns

The split established in ADR-025, made concrete:

```txt
POSTGRESQL                          OPENFGA
────────────────────────────────────────────────────────────────
Person records                      person → tenant membership
Membership status, dates, plan      person → org unit relationships
Invoice, charge, payment            person → resource entitlement
Booking, stay, allocation           person → role @ scope
Programme, offering, occurrence     org unit → authorization parent
Policy definitions                  org unit → authority verbs → org unit
Verification records                office → confers → role
Consumption records, obligations    consumption type → tenant
Office holding (with terms)         cross-tenant grants
Audit log                           JIT / break-glass grants
```

The test for which store a fact belongs in:

> Does this fact exist for a reason other than authorization?
> Yes → PostgreSQL is the origin, OpenFGA holds a synchronized edge.
> No → OpenFGA is simply the only store.

## 5.0.6 Aggregate roots

One list, so that transaction boundaries are visible in one place.

| Context      | Aggregate roots                                                                    |
| ------------ | ---------------------------------------------------------------------------------- |
| Organization | `Tenant`, `OrganizationalUnit`, `Affiliation`                                      |
| Identity     | `Person`, `Guardianship`                                                           |
| Membership   | `Membership`, `MembershipPlan`, `MembershipApplication`                            |
| Programme    | `Programme`, `Offering`, `Enrollment`                                              |
| Resource     | `Resource`, `Booking`, `Stay`                                                      |
| Governance   | `Office`, `OfficeHolding`, `Committee`, `DecisionRecord`                           |
| Policy       | `PolicyDefinition`                                                                 |
| Finance      | `Invoice`, `Payment`                                                               |
| Safeguarding | `Verification`, `Restriction`                                                      |
| Consumption  | `ConsumptionType`, `ConsumptionObligation`, `ConsumptionRecord`, `ExpectedAbsence` |

**`Allocation` is deliberately not an aggregate root.** It is a shared table
beneath `Booking` and `Stay`, existing solely to carry the exclusion
constraint that enforces non-overlapping use of a resource. Neither aggregate
owns it; both write into it. This is the one place where the design
knowingly trades aggregate purity for an invariant that cannot be safely
enforced twice (ADR-058, ADR-059).

## 5.0.7 Consistency boundaries

```txt
STRONGLY CONSISTENT (single Postgres transaction)
    business mutation + outbox row
    allocation exclusivity
    invoice and its charges

SYNCHRONOUS ACROSS STORES (before operation is externally effective)
    role revocation
    membership suspension
    affiliation sanction
    restriction creation
    JIT grant expiry

EVENTUALLY CONSISTENT (outbox dispatch, sub-second target)
    role grant
    new relationship creation
    entitlement addition
```

The asymmetry is deliberate: **granting may lag; revoking may not.**

## 5.0.8 Cross-context communication

Three permitted mechanisms, in order of preference:

1. **Authorization check** — any context may call `check(...)`. This is not
   coupling; it is the point.
2. **Domain event via outbox** — the only way state changes propagate
   between contexts.
3. **Synchronous query through a published interface** — permitted, but each
   instance is a coupling to be justified in the subsection.

Explicitly prohibited: reading another context's tables, and sharing a
transaction across contexts.

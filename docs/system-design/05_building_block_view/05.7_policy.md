# 05.7 — Policy

Owns policy definitions, their inheritance across organizations, and their
evaluation.

The context most at risk of becoming a general-purpose rules engine, and the
one where restraint matters most. Policies here are **typed domain objects
with known semantics** — not stored code, not a DSL, not a scripting host
(ADR-033).

---

## 5.7.1 Responsibilities

### Owns

- `PolicyType` — system-defined; the known semantics
- `PolicyDefinition` — a tenant's or body's instance of a type
- `PolicyBinding` — where a definition applies
- Resolution — computing the effective policy at a point in the graph
- Evaluation — answering a policy question

### Does not own

- Authorization (that is OpenFGA) — a policy never grants access
- The domain decisions policies inform — those belong to the context asking

---

## 5.7.2 Policy is a typed object, not code

```txt
PolicyType                 system-defined, versioned with the platform
    code                   MINIMUM_AGE, CANCELLATION_WINDOW,
                           OPENING_HOURS, MAX_DEPENDENTS,
                           CLEARANCE_REQUIRED, SUSPENSION_THRESHOLD, ...
    value_schema           the shape of a valid value
    inheritance_semantics  CONSTRAINT | OVERRIDE | DEFAULT | SET | APPEND
    comparator             for CONSTRAINT types: which direction is stricter
```

```txt
PolicyDefinition
    id
    policy_type_code
    owner_org_id            who published it
    level                   MANDATORY | DEFAULT | LOCAL
    value                   conforming to value_schema
    effective_from
    effective_until
    decision_record_id      nullable → how it was adopted
    status                  DRAFT | ACTIVE | SUPERSEDED
```

**Why not arbitrary expressions.** A policy that can contain any expression
is a code-execution surface stored in a database, evaluated with the
platform's privileges, authored by tenants. It cannot be statically
validated, cannot be reasoned about across inheritance, and cannot be safely
migrated. Every policy the movement actually needs — age minimums,
cancellation windows, opening hours, clearance requirements — is expressible
as a typed value.

Adding a policy type is a platform release. That friction is the feature: it
forces someone to decide what the type _means_ before tenants can use it.

---

## 5.7.3 The three levels

```txt
MANDATORY   published by a body with may_set_policy; cannot be
            overridden by anyone below (ADR-035)

DEFAULT     published upward; applies unless a lower body
            defines its own

LOCAL       the tenant's own; applies within its scope
```

Local policy may **tighten** an inherited constraint. It may not loosen a
`MANDATORY` one. There is no override mechanism and no contest workflow —
that was considered and rejected as scope creep (ADR-035).

```txt
MANDATORY minimum_age = 18
LOCAL     minimum_age = 21     ✓ tighter, permitted
LOCAL     minimum_age = 16     ✗ rejected at definition time
```

Rejection happens when the definition is **created**, not when it is
evaluated. A tenant should discover the conflict while authoring, not
silently have their intent ignored at runtime.

---

## 5.7.4 Inheritance semantics are per type

There is no universal inheritance algorithm (ADR-036). Each `PolicyType`
declares how its values combine.

### CONSTRAINT — strictest wins

```txt
Global    minimum_age >= 16
National  minimum_age >= 18
Local     minimum_age >= 21
                ↓
Effective minimum_age >= 21
```

Monotonic. No override semantics needed; the values simply accumulate. The
`comparator` on the type declares which direction is stricter — `>=` types
take the maximum, `<=` types take the minimum.

### OVERRIDE — nearest wins

```txt
Global    gym_closing_time = 22:00
National  gym_closing_time = 21:00
Local     gym_closing_time = 22:30
                ↓
Effective gym_closing_time = 22:30
```

Opening hours are not monotonic. A local association legitimately opens later
than its national body's default. Only a `MANDATORY` definition blocks this.

### DEFAULT — inherited unless locally defined

Identical resolution to OVERRIDE but semantically distinct: the upstream
value is advisory and expects local variation. Kept separate so that "nobody
set this locally" and "someone deliberately matched the default" are
distinguishable.

### SET — union of all levels

```txt
Global    accepted_id_types = {passport}
National  accepted_id_types = {aadhaar, pan}
Local     accepted_id_types = {student_card}
                ↓
Effective {passport, aadhaar, pan, student_card}
```

### APPEND — ordered concatenation

For types where sequence matters — escalation chains, notification ladders.
Upstream entries precede local ones.

## 5.7.5 Bindings

A definition is published by a body. A **binding** says where it applies.

```txt
PolicyBinding
    id
    policy_definition_id
    target_type          TENANT | ORG_UNIT | RESOURCE_TYPE |
                         RESOURCE | PROGRAMME | MEMBERSHIP_PLAN
    target_id
    propagates           boolean
```

Separating definition from binding lets one definition apply in several
places without duplication, and lets a national body publish a policy that
binds to every affiliate holding a particular relationship.

### Binding requires authority

```txt
A body may bind a MANDATORY policy to another tenant
only if it holds may_set_policy over that tenant.
```

The check is against the authority graph in 05.1.5 — not against affiliation,
which confers nothing. A national body without `may_set_policy` may publish
policies all it likes; they bind to nothing outside its own tenant.

This is the mechanism by which the five authority verbs become operative
rather than decorative.

## 5.7.6 Resolution

```txt
resolve(policy_type, target) → EffectivePolicy

  1. walk the authorization containment DAG upward from target
  2. collect every ACTIVE, in-window definition bound to any node
     on any path, plus any bound via may_set_policy from another tenant
  3. partition by level
  4. if any MANDATORY exists:
         apply type semantics across MANDATORY definitions
         reject any lower definition that loosens the result
  5. apply type semantics across the remainder, nearest-first
  6. return value + provenance
```

### Provenance is mandatory

```txt
EffectivePolicy
    policy_type_code
    value
    contributions []      { definition_id, owner_org, level, value }
    resolved_at
```

"Why is the minimum age 21 here?" must be answerable without reading code.
Every resolution carries the chain of definitions that produced it. A policy
system that returns a bare value is unauditable, and this one governs
constitutional matters.

### The DAG complicates this

Because authorization containment is a DAG (ADR-016), a target may inherit
from several paths that disagree.

```txt
Procter Pool
 ├── via Procter Chapter    → gym_closing_time = 21:00
 └── via PE Department      → gym_closing_time = 22:00
```

**Resolution rule for multi-path conflicts:**

```txt
CONSTRAINT types    strictest across all paths — always well-defined
SET / APPEND        union across all paths — always well-defined
OVERRIDE / DEFAULT  ambiguous; requires explicit disambiguation
```

For `OVERRIDE` and `DEFAULT` types, a resource with conflicting inherited
values from multiple paths must have a `LOCAL` definition, or resolution
fails loudly. Silently picking a path would make the answer depend on
traversal order.

This is checked when the edge or binding is created, so the conflict is
surfaced at configuration time rather than at 21:00 on a Tuesday.

## 5.7.7 Evaluation

Resolution produces a value. **Evaluation** answers a question, and it
happens in the asking context, not here (ADR-037).

```txt
Policy Service        resolve(MINIMUM_AGE, plan) → 21
        ↓
Membership Context    is this applicant 21? → yes/no
        ↓
Eligibility decision
```

```txt
Policy definitions
      ↓
Domain policy evaluation      ← the domain owns this
      ↓
Eligibility / authorization decision
```

The Policy context knows what the rule _is_. The domain context knows what
the rule _means_ for its objects. OpenFGA is not involved at all — a policy
never grants access; it constrains an operation the authorization graph has
already permitted in principle.

**Where an existing policy engine fits** — for genuinely complex conditional
evaluation — it is used rather than built, sitting behind the evaluation
interface. The typed-definition model above is unaffected by that choice.

## 5.7.8 Policies the platform ships

The initial `PolicyType` catalogue. Adding to it is a platform release.

| Code                        | Semantics              | Consumed by              |
| --------------------------- | ---------------------- | ------------------------ |
| `MINIMUM_AGE`               | CONSTRAINT ≥           | Membership, Programme    |
| `MAXIMUM_AGE`               | CONSTRAINT ≤           | Membership               |
| `MAX_DEPENDENTS`            | CONSTRAINT ≤           | Membership               |
| `SUSPENSION_THRESHOLD_DAYS` | CONSTRAINT ≤           | Membership, Finance      |
| `CANCELLATION_WINDOW`       | CONSTRAINT ≥           | Resource                 |
| `OPENING_HOURS`             | OVERRIDE               | Resource                 |
| `ACCESS_MODE_DEFAULT`       | OVERRIDE               | Resource                 |
| `CLEARANCE_REQUIRED`        | CONSTRAINT (strictest) | Safeguarding, Governance |
| `CLEARANCE_VALIDITY_MONTHS` | CONSTRAINT ≤           | Safeguarding             |
| `ACCEPTED_ID_TYPES`         | SET                    | Safeguarding, Resource   |
| `STAFF_MEMBERSHIP_POLICY`   | OVERRIDE               | Membership               |
| `SCREENING_ENABLED`         | OVERRIDE               | Safeguarding             |
| `JIT_MAX_DURATION`          | CONSTRAINT ≤           | Platform                 |
| `CROSS_TENANT_MAX_DURATION` | CONSTRAINT ≤           | Organization             |
| `PRICE_SELECTION_RULE`      | DEFAULT                | Programme                |
| `AGE_OF_MAJORITY`           | OVERRIDE               | Identity                 |

Note that `JIT_MAX_DURATION` and `CROSS_TENANT_MAX_DURATION` are
`MANDATORY`-level platform policies. The platform is itself a policy-setting
body over every tenant for a small, fixed set of security constraints — and
that authority is expressed through the same mechanism as everything else,
not as a special case.

## 5.7.9 Published events

```txt
PolicyDefinitionActivated    → all contexts binding that type
PolicyDefinitionSuperseded   → all contexts
PolicyBindingCreated         → affected targets
PolicyConflictDetected       → the authoring body, at definition time
```

Policy changes do **not** retroactively alter snapshotted values. A
cancellation policy captured on a booking (05.5.5) and a price captured on an
enrollment (05.4.5) are unaffected by later policy changes. This is the
snapshot pattern, and it is why those fields are snapshots rather than
references.

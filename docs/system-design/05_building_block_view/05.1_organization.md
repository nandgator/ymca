# 05.1 — Organization

The upstream context. Owns tenants, organizational structure, affiliation
between organizations, and the authority grants that connect them.

Every other context depends on this one for the tenant that anchors all its
data. Nothing here depends on anything downstream.

---

## 5.1.1 Responsibilities

### Owns

- `Tenant` — a sovereign association
- `OrganizationalUnit` — typed subdivisions, arbitrary depth
- Three independent containment relationships
- `Affiliation` — stateful relationship between organizations
- `AuthorityGrant` — the five verbs, granted explicitly
- `CrossTenantGrant` — time-bounded authority across a tenant boundary

### Does not own

- People, memberships, roles, or anything a person holds — those are
  Identity, Membership and Authorization respectively
- Physical addresses as first-class assets — a `Location` here is a
  descriptive attachment, not a property-management concept

---

## 5.1.2 Domain model

```txt
Tenant
 │  the sovereign boundary; root of every authorization path
 │
 ├── OrganizationalUnit *
 │      type: CHAPTER | DEPARTMENT | CENTRE | REGION | INSTITUTE | PROJECT
 │      │
 │      ├── org_parent        → OrganizationalUnit | Tenant   (0..1)
 │      ├── physical_location → Location                      (0..1)
 │      └── auth_parents      → node *                        (0..n)
 │
 ├── Affiliation *            → other Tenant
 ├── AuthorityGrant *         → other Tenant
 └── CrossTenantGrant *       → other Tenant, scoped, expiring
```

### Tenant

```txt
Tenant
    id                 opaque
    legal_name
    display_name
    jurisdiction       drives tax, screening availability, data residency
    status             ACTIVE | SUSPENDED | ARCHIVED
    created_at
```

`jurisdiction` is load-bearing rather than decorative. It determines which
tax calculator applies, whether registry screening is even available, and
whether the tenant may be hosted in this regional instance at all.

A tenant has **no parent field.** Relationships to other tenants exist only
as `Affiliation` and `AuthorityGrant` rows. This is the schema-level
expression of Principle 2.

### OrganizationalUnit

```txt
OrganizationalUnit
    id
    tenant_id          immutable after creation
    type               CHAPTER | DEPARTMENT | CENTRE | REGION |
                       INSTITUTE | PROJECT
    name
    org_parent_id      nullable → OrganizationalUnit
    location_id        nullable → Location
    status             ACTIVE | INACTIVE | ARCHIVED
```

One typed concept, not six (ADR-094). Depth is arbitrary and varies within a
single tenant — some regions subdivide into zones and sub-regions while their
peers do not, so no fixed level structure exists.

`tenant_id` is immutable. Moving a unit between tenants is not an update; it
is a decommission and a re-creation, because everything scoped beneath it
would otherwise silently change sovereignty.

## 5.1.3 The three containments

This is the heart of the context and the most commonly misunderstood part of
the design.

```txt
ORGANIZATIONAL      org_parent_id       who administers this unit
PHYSICAL            location_id         where it physically sits
AUTHORIZATION       auth_parent edges   how authority propagates
```

They are permitted to disagree, and in practice they do:

```txt
Physical Education Department
    org_parent      → YMCA Bombay          administered by the association
    location        → (none)               a department, not a place

Procter Pool                               (a Resource, but scoped here)
    physical        → 18 YMCA Road         located at Procter
    auth_parents    → Procter Chapter      local operational authority
                    → PE Department        functional authority
```

Both the Procter branch secretary and the PE department head hold authority
over that pool, by different paths. Modelling this with a single tree forces
one of them to be wrong.

### Authorization containment is a DAG

```txt
AuthorizationEdge
    child_id           any authorization object
    parent_id          any authorization object
    created_by
    created_at
```

**Invariants enforced on every write:**

1. No cycles. Detected before commit, not by a background job.
2. Both endpoints resolve to the same tenant ancestor, unless the edge is a
   `CrossTenantGrant` (below).
3. Path depth bounded — a configured maximum, defaulting to 12, to prevent
   pathological fan-out in FGA evaluation.
4. Edges are created explicitly. Creating an `OrganizationalUnit` with an
   `org_parent` does **not** implicitly create an authorization edge.

That last invariant is the one that will feel wrong to implementers and must
not be relaxed. Auto-creating the edge collapses authorization containment
back into organizational containment, which is precisely the mistake this
context exists to prevent. The unit-creation _workflow_ may offer to create
the matching edge; the _model_ must not do it silently.

**Given real teeth as of step 8.3.5.** `POST /t/{t}/units` (A3.7) is the
first endpoint that can insert an authorization edge, so invariant 1 above
is no longer a rule waiting for a write path to matter to. It is specified
to check `admin` on whichever parent the request names — the tenant itself
for a top-level unit, an existing unit for a nested one — and to write the
unit row and its edge together in one transaction, running the pre-commit
recursive CTE (A2.2, depth 12) before either commits, and offering the
matching edge explicitly per invariant 4 rather than deriving it. The check
itself is code, not yet written — 11.2 closes the "cycle check unimplemented"
gap only once that code and its migration land. `GET /t/{t}/units/{unit}`
checks `member` on the named unit; a tenant admin already reaches it through
`member from auth_parent` (A1.2), so no relation changed for that endpoint.

`GET /t/{t}/units/{unit}/members` (owned by Identity, 05.2, not this
context) lists memberships scoped to the named unit alone, never its
descendants — ADR-104's list-authorizes-the-scope mechanism applied to a
scope this context owns. A caller authorized at a parent unit reaches a
child's members by naming the child; the parent's own list never folds them
in. Recorded here because the scope object is an `organizational_unit`, even
though the rows listed are not.

## 5.1.4 Affiliation

```txt
Affiliation
    id
    from_tenant_id      the recognizing body
    to_tenant_id        the affiliate
    state               APPLIED
                      | AFFILIATED_IN_GOOD_STANDING
                      | AFFILIATED_IN_ARREARS
                      | SUSPENDED
                      | LAPSED
                      | WITHDRAWN
    since
    last_reviewed_at
```

### State machine

```txt
                    APPLIED
                       │ accepted
                       ▼
        ┌──── AFFILIATED_IN_GOOD_STANDING ────┐
        │              ▲        │              │
   dues unpaid         │        │ sanction     │ voluntary
        ▼              │        ▼              ▼
  AFFILIATED_IN_ARREARS│    SUSPENDED      WITHDRAWN
        │              │        │
        │  remedied ───┘        │ not remedied
        │                       ▼
        └──────────────────▶ LAPSED
```

### Affiliation confers nothing

The single most important statement in this subsection. An `Affiliation` row
grants no capability whatsoever. It records that two organizations recognize
one another. Every power flows from a separate `AuthorityGrant`.

```txt
Affiliation(India → Bombay)          "we recognize each other"
AuthorityGrant(India → Bombay,
               may_set_policy)       "and India may set policy"
```

Delete the second row and India retains the affiliation and loses the power.
That separation is testable and should be tested.

### Non-affiliation is normal

A tenant may exist with no `Affiliation` rows at all (ADR-075). In the Indian
movement roughly 450 local associations are non-affiliated against 588
affiliated — a model presuming affiliation would exclude nearly half the
addressable movement. Affiliation is acquired, never presumed, and never a
precondition for using the platform.

## 5.1.5 Authority grants

```txt
AuthorityGrant
    id
    from_tenant_id
    to_tenant_id
    verb            may_set_policy
                  | may_review_compliance
                  | may_sanction
                  | may_administer
                  | may_read_member_data
    granted_by      who established this
    granted_at
    basis           free text: constitutional, contractual, statutory
    expires_at      nullable
```

Five verbs, granted independently (ADR-009). No verb implies another, and
there is no "all" value — granting four verbs requires four rows, visible
individually in any audit.

**Three of the five resolve in the graph; two are recorded and resolve to
nothing** (ADR-102):

```txt
may_set_policy          act ON the affiliation      resolves
may_review_compliance   act ON the affiliation      resolves
may_sanction            act ON the affiliation      resolves

may_administer          would act THROUGH it        recorded only
may_read_member_data    would act THROUGH it        recorded only
```

The two that would reach into the target tenant are stored so that holding
them is auditable, and grant nothing. A body that must genuinely administer
or read uses a `CrossTenantGrant` — one object, an approver, a reason, an
expiry. The refusal is enforced by the assertions in A1.7, not by convention.

### Typical configurations

```txt
NATIONAL BODY → LOCAL ASSOCIATION   (the common federated case)
    may_set_policy            ✓
    may_review_compliance     ✓
    may_sanction              ✓
    may_administer            ✗
    may_read_member_data      ✗
```

This is the configuration the whole architecture was built to express: a
national body that can bind a local association to standards, audit its
compliance, and suspend its affiliation for failing — while being structurally
incapable of reading one member record.

```txt
REGIONAL BODY → LOCAL ASSOCIATION   (weaker, coordination only)
    may_set_policy            ✓ (DEFAULT-level policies only)
    everything else           ✗

PEER → PEER                          (specialist recognition, ADR-008)
    authority flowing sideways or upward is expressed the same way
```

### `may_sanction` is scoped to the relationship

The critical invariant, stated in code terms:

```txt
sanction(actor, target_affiliation, grounds)
    → may change Affiliation.state
    → may revoke brand-use permission
    → may impose conditions

    → may NOT read, write or reach any object
      whose tenant ancestor is the target
```

A sanction acts on the affiliation, never through it.

## 5.1.6 Cross-tenant grants

The single sanctioned exception to Principle 1, deliberately made
uncomfortable to use.

```txt
CrossTenantGrant
    id
    from_tenant_id      granting tenant
    to_subject          person or org unit in another tenant
    scope_object_id     the specific object authority applies to
    permissions []      explicit list, no wildcards
    reason              required, free text
    approved_by         must hold authority in from_tenant
    granted_at
    expires_at          required, non-null, bounded by policy maximum
    revoked_at
```

**Constraints:**

- `expires_at` is mandatory. There is no permanent cross-tenant grant.
- `scope_object_id` names one object. There is no tenant-wide cross grant.
- `permissions` is explicit. No wildcards, no role references that could
  later widen.
- Creation and every use emit audit events.
- Maximum duration is a `MANDATORY`-level platform policy.

```txt
Example
    regional_body ──grants──> org_unit:bombay
        scope:        programme:regional-youth-2026
        permissions:  [programme.manage, enrollment.read]
        expires:      2027-03-31
        reason:       "Bombay administering regional youth programme
                       per Council resolution 2026/14"
```

Cross-tenant authority is never containment-derived (ADR-019). It exists as
a row, with a reason, an approver and an expiry, or it does not exist.

## 5.1.7 Location

```txt
Location
    id
    tenant_id
    address_lines []
    city, region, country, postcode
    coordinates      nullable
```

Deliberately thin. A `Location` is descriptive — it exists so that a unit or
resource can say where it is. It is not a property-management entity, carries
no capacity, and confers no authority.

An `OrganizationalUnit` may exist with no location (a department), and
several units may share one (a branch and its departments at one address).

## 5.1.8 Published events

```txt
TenantCreated                  → Authorization, Platform
TenantSuspended                → all contexts
OrganizationalUnitCreated      → Authorization
OrganizationalUnitArchived     → Authorization, Resource, Programme
AuthorizationEdgeCreated       → Authorization
AuthorizationEdgeRemoved       → Authorization  (synchronous)
AffiliationStateChanged        → Governance, Finance
AuthorityGranted               → Authorization
AuthorityRevoked               → Authorization  (synchronous)
SanctionImposed                → all contexts, high-severity audit
CrossTenantGrantCreated        → Authorization
CrossTenantGrantExpired        → Authorization  (synchronous)
```

Events marked synchronous follow the revocation rule from 05.0.7: authority
removal is written to OpenFGA before the operation is externally effective.

## 5.1.9 Authorization model fragment

The FGA types this context contributes. Full schema in A1.

```txt
type tenant
  relations
    define platform_operator: [platform_role]

type organizational_unit
  relations
    define tenant: [tenant]
    define auth_parent: [organizational_unit, tenant]
    define member: [person] or member from auth_parent
    define admin:  [person] or admin  from auth_parent

type affiliation
  relations
    define from_tenant: [tenant]
    define to_tenant:   [tenant]

    define may_set_policy:        [principal]
    define may_review_compliance: [principal]
    define may_sanction:          [principal]

    # Recorded, resolve to nothing. ADR-102
    define may_administer:        [principal]
    define may_read_member_data:  [principal]
```

Note that `affiliation` is a first-class FGA object with its own relations.
This is what allows `may_sanction` to be granted **on the affiliation** rather
than on the target tenant — the structural guarantee that sanction authority
cannot leak into data access.

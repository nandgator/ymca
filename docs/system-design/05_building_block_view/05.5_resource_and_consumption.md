# 05.5 — Resource and Consumption

Owns the facilities and how their capacity is consumed: resources, the
windows that govern how they may be used, the allocation table that prevents
double-booking, and the two independent aggregates that consume it.

This is the context where the design knowingly trades aggregate purity for an
invariant, and the reasoning is set out in full because a future contributor
will otherwise "fix" it.

---

## 5.5.1 Responsibilities

**Owns**

- `ResourceType` — tenant-defined, archetype-bound
- `Resource` — the facility itself
- `AccessWindow` — when and how a resource may be used
- `Allocation` — the exclusivity substrate
- `Booking` — discrete slot consumption
- `Stay` — continuous accommodation
- `CancellationPolicy` binding — via Policy (05.7)

**Does not own**

- Entitlement to use anything (Membership, 05.3)
- Programmes that consume resources (Programme, 05.4)
- Money (Finance, 05.8)

---

## 5.5.2 Resource types and archetypes

A resource type is tenant-defined but must declare a **system archetype**
(ADR-077).

```txt
ResourceType
    id
    tenant_id
    name                  tenant's own vocabulary
    archetype             BOOKABLE_SLOT | ALLOCATABLE_UNIT
                        | WALK_IN_ONLY | NON_CONSUMABLE
    default_access_mode
```

```txt
BOOKABLE_SLOT     consumed for a discrete period; capacity per slot
                  pool lanes, squash courts, halls

ALLOCATABLE_UNIT  consumed continuously by one occupant at a time
                  hostel beds, private rooms, lockers

WALK_IN_ONLY      entitlement and opening hours only, no reservation
                  library, table tennis, gym floor

NON_CONSUMABLE    exists, may be referenced, has no capacity
                  a chapel, a garden
```

**Why archetypes rather than a closed taxonomy.** A fixed list of
`POOL | GYM | HOSTEL_ROOM | HALL` makes every new facility type a platform
release, and a global movement will encounter types nobody anticipated —
camp sites, vocational workshops, tribal development centres, a college of
physical education. A fully open type system makes behaviour unpredictable
and cross-tenant reporting meaningless. Archetypes fix the behaviour and free
the vocabulary.

```txt
Resource
    id
    tenant_id
    resource_type_id
    org_unit_id           administrative owner
    location_id           nullable → Location; physical placement
    name
    capacity              nullable; meaning depends on archetype
    parent_resource_id    nullable; a bed within a room
    status                ACTIVE | MAINTENANCE | RETIRED
```

`org_unit_id` and `location_id` may disagree, and the authorization parents
may be different again — the three-containment rule from 05.1.3 applies to
resources as much as to org units.

### Rooms and beds

```txt
Resource(Room 101)          archetype ALLOCATABLE_UNIT
    allocation_unit = BED
    ├── Resource(101-A)     bed
    └── Resource(101-B)     bed

Resource(Room 205)          archetype ALLOCATABLE_UNIT
    allocation_unit = ROOM
    (no children; the room is allocated whole)
```

Granularity varies by room type (ADR-064). A shared dormitory allocates beds
independently; a private room is allocated as one unit. Both are the same
archetype with a different `allocation_unit`.

## 5.5.3 Access windows

Whether a resource is walk-in or booked is a property of a **time window**,
not of the resource (ADR-060).

```txt
AccessWindow
    id
    resource_id
    schedule_rule         recurrence expression
    starts_time
    ends_time
    access_mode           WALK_IN | BOOKED
    capacity              nullable; enforced only for BOOKED
    entitlement_required  nullable → EntitlementGrant target
    valid_from
    valid_until
```

```txt
Procter Pool
 ├── 06:00–09:00   WALK_IN   free swim
 ├── 09:00–21:00   BOOKED    lane sessions, capacity 8
 └── 21:00–22:00   BOOKED    club hire, capacity 1
```

Real pools and gyms run both modes on the same physical resource at different
hours. Putting `access_mode` on the resource makes that unrepresentable.

Access mode is resolvable as tenant or branch policy (ADR-060 with ADR-034),
so one association may run its pools walk-in while another books them, without
either being a special case.

### Walk-in capacity is not enforced

```txt
BOOKED window     capacity real, enforced, allocations created
WALK_IN window    entitlement + opening hours only; no capacity check
```

The physical mechanism to count live occupancy does not exist at most sites
(ADR-061). Rather than pretend, the model enforces nothing for walk-in
windows.

**Design note.** `capacity` sits on the *window*, not the resource, so a site
that later installs access control can enable capacity tracking on a
walk-in window without a schema change. The field is present and unused
rather than absent.

## 5.5.4 Allocation — the exclusivity substrate

```txt
Allocation
    id
    resource_id
    period                tstzrange
    consumer_type         BOOKING | STAY | OCCURRENCE | MAINTENANCE
    consumer_id
    created_at
```

```sql
EXCLUDE USING gist (
    resource_id WITH =,
    period      WITH &&
)
WHERE (consumer_type <> 'SHARED')
```

### Why this exists

`Booking` and `Stay` are independent aggregates with independent state
machines (ADR-058). No shared abstract parent. That was the right domain
decision — a pool slot and a six-week hostel residency share almost nothing
in lifecycle, approval, payment or cancellation.

But it leaves one invariant homeless:

> The same resource must not be allocated to overlapping periods.

Implemented twice in two aggregates, that invariant will drift. Implemented
once in the database, it cannot be bypassed by any code path — including
paths that do not exist yet.

```txt
Booking        ──writes──▶ Allocation ◀──writes── Stay
                               ▲
                               │
Occurrence ────writes──────────┘
```

Three writers, one constraint, one place to reason about it.

**`Allocation` is deliberately not an aggregate root** (05.0.6). Neither
Booking nor Stay owns it. This is a knowing departure from DDD orthodoxy, and
it is the correct trade: aggregate purity is a means to correctness, and here
it would cost correctness.

**It is also not in the authorization graph.** Whether a slot is free is
business state, not authority. Same reasoning that kept membership suspension
out of OpenFGA in 05.3.10.

`MAINTENANCE` as a consumer type lets a resource be taken out of service by
the same mechanism, rather than by a separate availability flag that
consumers would have to remember to check.

## 5.5.5 Booking

```txt
Booking
    id
    resource_id
    access_window_id
    actor_person_id           who booked
    beneficiary_person_id     who uses it — may differ (ADR-065)
    allocation_id             → Allocation
    invoice_id                nullable
    state
    cancellation_policy_id    → Policy, snapshotted at booking time
    created_at
```

### State machine

```txt
       REQUESTED
           │  capacity + entitlement
     ┌─────┴─────┐
     ▼           ▼
 WAITLISTED   CONFIRMED
     │           │
     │           ├──▶ CHECKED_IN ──▶ COMPLETED
     │           │
     │           ├──▶ NO_SHOW
     │           │
     └──────────▶└──▶ CANCELLED
```

Independent of `Stay`'s machine (ADR-058). They share no states, no
transitions and no supertype.

### Actor and beneficiary

```txt
actor        Alice   member, entitled, accountable for payment
beneficiary  Rahul   guest, no membership, uses the hall
```

Members book rooms and halls for guests. The guest must exist as a `Person`
record — the association needs to know who was in the building, which is a
safeguarding requirement as much as an operational one.

Entitlement is checked against the **actor**. Presence is recorded against
the **beneficiary**.

### Cancellation policy is snapshotted

`cancellation_policy_id` is captured at booking time and never re-read from
the current policy. A tenant tightening its cancellation terms must not
retroactively change the terms someone already accepted. Same principle as
the price snapshot in 05.4.5.

## 5.5.6 Stay

```txt
Stay
    id
    resource_id               a bed or a room, per allocation_unit
    person_id                 the resident
    booked_by_person_id       may differ
    allocation_id             → Allocation
    verification_id           → Verification; identity check
    approval_record_id        → DecisionRecord
    house_rules_accepted_at
    deposit_charge_id         nullable → Finance
    invoice_id                nullable
    state
    expected_check_out
    actual_check_out
```

### State machine

```txt
     REQUESTED
         │
         ▼
    UNDER_REVIEW              approval required (ADR-063)
         │
   ┌─────┴─────┐
   ▼           ▼
DECLINED    APPROVED
               │
               ▼
           CONFIRMED
               │
               ▼
           CHECKED_IN ──▶ EXTENDED ──┐
               │                     │
               │◀────────────────────┘
               ▼
          CHECKED_OUT
               │
               ▼
      DEPOSIT_SETTLED ──▶ COMPLETED
```

Genuinely different from `Booking`: approval before confirmation, identity
verification, house-rules acceptance, extension mid-stay, and a deposit
settlement step after departure. Forcing these into a shared state machine
with pool bookings would produce a union of states where most are invalid for
most instances.

### Extension

An extension is a **new allocation** appended to the stay, not a mutation of
the existing period. If the adjacent period is already allocated, the
extension fails at the database constraint rather than in application logic.

### Approval

Stays require approval (ADR-063) — the same permission-resolution mechanism
as membership admission, routed through Governance to whoever actually holds
`stay.approve` at the relevant scope.

## 5.5.7 Entitlement to use a resource

The read path, and the clearest example of Principle 3 in the whole document.

```txt
Question 1   May Alice ever use the pool?
             → resolve_entitlements(alice, tenant)  [05.3.8]
             → does any bundle grant this resource or its type?
             → AUTHORIZATION

Question 2   May Alice swim at 18:00 on Tuesday?
             → is there an AccessWindow covering that time?
             → BOOKED: capacity remaining? allocation free?
             → WALK_IN: within opening hours? (no capacity check)
             → suspension active? booking window open?
             → DOMAIN
```

These are separate questions with separate answers and separate failure
messages. A member denied at question 1 needs to buy a subscription; a member
denied at question 2 needs a different time slot. Conflating them produces
the "access denied" that tells nobody anything.

## 5.5.8 Published events

```txt
ResourceRetired            → Programme  (occurrences must reschedule)
AccessWindowChanged        → (bookings already made are unaffected)
BookingConfirmed           → Finance
BookingCancelled           → Finance  (cancellation policy applies)
BookingNoShow              → (tenant policy may penalise)
StayApproved               → Finance  (deposit charge)
StayCheckedIn              → Safeguarding  (occupancy record)
StayCheckedOut             → Finance  (deposit settlement)
AllocationReleased         → Programme  (waitlist seam, deferred)
```

## 5.5.9 Authorization model fragment

```txt
type resource
  relations
    define tenant: [tenant]
    define org_unit: [organizational_unit]
    define auth_parent: [organizational_unit, resource]
    define manager: [person] or admin from auth_parent
    define entitled: [entitlement_bundle#beneficiary]
```

`entitled` is the union of every bundle granting this resource. `manager` is
role-derived and propagates from the authorization parents — which, per
05.1.3, may include both the branch where the pool sits and the department
that operates it.

Bookings, stays and allocations are **not** in the graph. They are business
facts with periods and states. The graph answers whether Alice is entitled to
the resource; PostgreSQL answers whether the slot is free.

## 5.5.11 Open items

| Item | Note |
|---|---|
| Overbooking | Some tenants may want deliberate overbooking on low-show resources; the exclusion constraint currently forbids it absolutely |
| Recurring bookings | A weekly squash slot is currently N independent bookings |
| Resource groups | "Any available lane" rather than a named lane — not modelled |
| Deposit forfeiture | The settlement step exists; the rules for partial forfeiture are Finance's and unspecified |
| Walk-in occupancy | `capacity` is present and unused on walk-in windows, awaiting sites with access control |

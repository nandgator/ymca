# 05.10 — Consumption

The record of what was actually used, as distinct from what was reserved.

This context was added after the original nine, when the reference tenant's
own requirement — a hostel mess register — proved inexpressible. It is
written to implementation-ready depth because the first release depends on it.

---

## 5.10.1 Responsibility

### Owns

- `ConsumptionType` — tenant-defined, declares whether it obligates
- `ConsumptionObligation` — a standing expectation of use
- `ConsumptionRecord` — one occurrence of actual use
- `ExpectedAbsence` — a declared future non-use
- `ConsumptionOption` — the tenant's catalogue of priced variations

### Does not own

- Whether a person may consume at all (Membership, 05.3)
- Exclusivity of a resource (Resource, 05.5)
- Money (Finance, 05.8)
- Who may record on whose behalf (Authorization, 08.1)

---

## 5.10.2 Reservation and realization

The distinction that justifies a separate context.

```txt
Booking, Stay      RESERVED use     creates an Allocation
Consumption        ACTUAL use       creates no Allocation
```

`Allocation` exists solely to carry the exclusion constraint (05.0.6). A meal
excludes nobody. A gym entry excludes nobody. Forcing consumption through
`Allocation` would put a GiST exclusion constraint in the write path of the
highest-frequency, lowest-value operation in the system, to enforce an
invariant that does not apply.

A record **may** name the allocation it realizes:

```txt
booked a lane, attended     Booking + Allocation + ConsumptionRecord
booked a lane, no-show      Booking + Allocation, no record
walked into the gym         ConsumptionRecord alone
ate dinner                  ConsumptionRecord alone
```

This is what `WALK_IN_ONLY` (05.5.2) has always lacked. That archetype
enforces nothing and, until now, recorded nothing — so walk-in use was
invisible to billing, attendance and reporting alike.

## 5.10.3 Consumption types

Tenant-defined, following the archetype discipline of ADR-077.

```txt
ConsumptionType
    id
    tenant_id
    name                  tenant vocabulary: "Dinner", "Gym entry"
    resource_id           nullable; what is consumed, if anything
    obligates             boolean          ← the load-bearing field
    recurrence            DAILY | WEEKLY | PER_OCCURRENCE   (when obligates)
    record_mode           SELF | STAFF | EITHER
    correction_window     interval; null means no limit
```

### `obligates` is the whole absence model

The reference tenant bills dinner when no record exists and does not bill
breakfast. The obvious modelling — an `absence_default` per type — is wrong,
because it makes the bill reference rows that do not exist.

Obligation inverts it:

```txt
Dinner      obligates = true   DAILY    residents owe dinner; absence must be excused
Breakfast   obligates = false           voluntary; no record means nothing happened
Gym entry   obligates = false           voluntary
```

Breakfast is not "not billed when absent." Breakfast has no obligation to be
absent from. The special case disappears rather than being configured.

**Obligation is opt-in and tenant-local.** The reference tenant obligates
dinner because its residents are on full board. Another association running the
same mess as a pay-per-meal canteen sets `obligates = false` and the same
machinery bills only what was recorded. The platform ships the switch.

## 5.10.4 Obligations are standing, not materialized

```txt
ConsumptionObligation
    id
    tenant_id
    consumption_type_id
    subject_person_id
    effective             tstzrange     while the source relationship holds
    source_type           STAY | MEMBERSHIP | SUBSCRIPTION
    source_id
```

**One row per person per type**, not one per person per day. A resident staying
nine months has one dinner obligation, not 270 rows.

Expected units are derived at billing time:

```txt
expected = recurrence × (effective ∩ billing_period)
         − periods relieved by ExpectedAbsence
```

Materializing a presumed record per person per day was rejected. It requires a
nightly job, and 8.7 is explicit that _sweepers exist only for notification and
cleanup — never for enforcement_. Billing from sweeper-written presumptions is
enforcement. It would also make a stalled job silently under-bill, which is
precisely the class of failure this design refuses elsewhere.

Obligations are created and ended by the source relationship — a `Stay`
beginning creates one, checkout ends it — never by a clock.

## 5.10.5 Consumption records

```txt
ConsumptionRecord
    id
    tenant_id
    consumption_type_id
    subject_person_id      who consumed
    actor_person_id        who recorded it; equal to subject for self-service
    occurred_on            date
    obligation_id          nullable; the obligation this discharges
    allocation_id          nullable; the reservation this realizes
    variant_code           nullable; typed by the consumption type
    supersedes_id          nullable; corrections
    recorded_at
```

```txt
ConsumptionRecordOption
    consumption_record_id
    consumption_option_id
```

`subject` and `actor` are separate for the same reason `Booking` separates
actor from beneficiary (12, _Actor vs Beneficiary_): a warden recording for a
resident and a resident recording for themselves are different facts, and the
audit trail must distinguish them.

### Options and variants

```txt
ConsumptionOption
    id
    tenant_id
    consumption_type_id
    code                  BOILED_EGG | MILK | OMELETTE
    name
    charge_component      kind + amount, contributed to the bill
    status                AVAILABLE | WITHDRAWN
```

A **variant** modifies the obligated unit and may carry a surcharge — the
reference tenant's veg / non-veg dinner. An **option** is an addition — a
boiled egg with breakfast. Both resolve to charge components; the distinction
is kept because a variant answers _what was the obligated thing_ and an option
answers _what was added to it_, and only the first can exist without the
second.

Variant is decided per record, never stored as a standing preference on the
person. A resident who ate non-veg on Tuesday has not declared themselves
non-vegetarian.

## 5.10.6 Expected absence

```txt
ExpectedAbsence
    id
    tenant_id
    subject_person_id
    period                 tstzrange
    declared_by_person_id
    relieves_recording     boolean, snapshotted
    relieves_payment       boolean, snapshotted
    decision_record_id     nullable; null when self-declared
    declared_at
    withdrawn_at
```

Absence relieves along two independent dimensions:

```txt
relieves_recording    the person need not submit records for the period
relieves_payment      obligated units in the period are not billed
```

The reference tenant's LONG and SHORT leave are these two flags, not an enum:

```txt
SHORT   relieves_recording = true    relieves_payment = false
LONG    relieves_recording = true    relieves_payment = true
```

Which flags apply is resolved by policy at declaration time —
`ABSENCE_PAYMENT_RELIEF`, a tenant policy carrying the threshold — and then
**snapshotted onto the row** (pattern 8.4). A tenant raising its threshold from
seven days to ten cannot retroactively rebill an absence already declared and
relieved. This is the same rule that protects a booked cancellation policy and
an enrolled price.

**Self-declaration is the default and approval is optional.** The reference
tenant requires none; `decision_record_id` accommodates tenants whose
constitution does. Absence is not suspension: entitlement is untouched
throughout, so nothing is written to OpenFGA and no synchronous revocation
path is involved.

## 5.10.7 Corrections, not edits

A consumption record is never mutated. A correcting record supersedes it.

```txt
record  r1   dinner, veg           occurred_on 2026-03-04
record  r2   dinner, non-veg       supersedes r1
```

This mirrors the rule already established for invoices — _issued invoices are
immutable; corrections are credit notes_ (A2.8) — and serves quality goal 2.
Mutable consumption history would make a disputed bill unanswerable, which is
the hostel's existing problem with a paper register, not a new one to import.

`correction_window` on the type bounds how late a correction may be filed.
Enforcement is at decision time against `occurred_on`; there is no lock job.
Beyond the window, a correction requires `consumption.correct_late`, which is
audited at `NOTABLE` severity.

The reference tenant's "Secretary may add an override note after midnight" is
this mechanism: a superseding record by a staff actor, not an edit.

## 5.10.8 Billing handoff

Consumption raises no money. It publishes, and Finance composes.

```txt
ConsumptionPeriodClosed
    tenant_id, subject_person_id, period
    obligated_units        expected, net of payment-relieving absences
    recorded_variants []   with their charge components
    recorded_options  []   with their charge components
```

Finance composes one charge:

```txt
Charge(source_type = CONSUMPTION, source_id = period)
    SUBSCRIPTION_FEE  RECURRING   flat board fee
    DISCOUNT          −ve         relieved obligated units
    USAGE_FEE                     options
    USAGE_FEE                     variant surcharges
    TAX
```

**This requires `CONSUMPTION` in `Charge.source_type`**, today
`MEMBERSHIP | SUBSCRIPTION | ENROLLMENT | BOOKING | STAY | DEPOSIT | DUES |
ADJUSTMENT` (05.8.3). A Published Language change per 05.0.4 — additive, and
the only change this context forces on another.

Consumption never writes to Finance tables and never computes an amount. It
reports units and vocabulary; pricing and tax are Finance's.

## 5.10.9 Authorization

```txt
consumption.record            record for oneself
consumption.record_for_other  staff recording on a resident's behalf
consumption.correct           supersede within the window
consumption.correct_late      supersede beyond it            NOTABLE
consumption.read              read another person's records
consumption.close_period      trigger the billing handoff
```

Entitlement to consume is **not** a permission here — it is resolved through
Membership entitlement bundles exactly as resource use is (05.3). The two-part
split of Principle 3 applies unchanged:

```txt
AUTHORIZATION   is this person entitled to this consumption type at all?
DOMAIN          is there an open obligation, is the window still open,
                is the type available today?
```

## 5.10.10 What this context does not decide

| Question                            | Resolved by                         |
| ----------------------------------- | ----------------------------------- |
| Whether consumption is obligated    | tenant, per type                    |
| What an option or variant costs     | tenant catalogue, priced by Finance |
| The absence relief threshold        | tenant policy                       |
| Whether absence needs approval      | tenant governance                   |
| How long corrections are accepted   | tenant, per type                    |
| Whether staff may record for others | tenant, via `record_mode` and roles |
